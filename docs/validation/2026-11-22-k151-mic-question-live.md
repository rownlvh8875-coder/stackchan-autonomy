## 오프라인 재현과 수정

WakeNet은 감지 이벤트를 반환한다. 이어지는 질문 진단은 기존 코덱을
해제하고 새 RX 채널을 열었지만, 처음 프레임부터 질문의 발화 시작
조건에 포함했다. 새 채널에서 60ms 연속으로 RMS 기준 이상인 입력이
들어온 뒤 500ms 동안 기준에 미달하면 질문 없이도 `endpoint`가 될 수 있었다.

실제 K151 포트와 질문 분리기 코드에 모의 I2S 입력을 연결했다. 전환 직후
80ms의 높은 에너지와 이후 기준 미달 입력만 공급한 시험은 수정 전
`endpoint`로 실패했다. 이 재현은 전환 입력을 질문과 구분하지 못하는
코드 경로를 확인한다. 지난 실물 시험의 고정 레코드로는 호출어 소리의
잔여분, RX 초기화 구간의 신호, 주변 소리 중 어떤 입력이 원인이었는지
특정할 수 없다.

질문 전용 진단은 새 RX에서 기존 RMS 기준에 연속 25프레임(500ms)
미달한 뒤에만 질문 안내를 보낸다. 기준을 넘는 프레임이 끼면 연속
카운트를 다시 시작한다. 안내까지 읽은 입력은 질문용 PSRAM에 복사하지
않으며 기존 프레임 지움 경로를 사용한다. 안내 전 한도를 소진하면
`quiet_timeout`, 안내 뒤 발화 종료 없이 한도를 소진하면
`no_endpoint`를 반환한다. 400프레임·8초의 질문 한도와 START 이후
10초의 전체 한도 안에 대기 시간도 포함된다.

회귀 시험은 초기 신호만 있는 경우의 `no_endpoint`, 안내 직후 유효한
합성 질문의 `endpoint`, 중간에 끊긴 조용한 구간, 연속 기준 미달 없이
소진된 시간 한도, 정확히 마감 때 조용해진 입력을 검사했다. 안내 전
STOP·부분 읽기, 안내 뒤 동의 철회·부분 읽기, 코덱 해제 실패와 PCM 지움도
확인했다. USB 검사기는 안내 전 `quiet_timeout`과 읽기 실패를 구분하고
종료 HOLD를 요구한다. 개인 호출어 경로와 기존 에너지 문턱은 유지했다.
이 수정의 검증 범위는 오프라인 시험이다. 적용 뒤 실물 결과는 아래에 기록한다.

## 짧은 호출어 단독 관찰

전체 START 한도는 기존 10초다. 오프라인에서는 실제 `BenchGate`와
K151 포트 코드에 모의 I2S 입력을 연결했다. 호출어 감지와 준비에 4초가
지난 조건에서 기존 길이로 질문을 기다리면 10초 한도에 걸려
`stopped`가 됐다. 같은 입력을 짧은 대조 모드에 공급하면 START
약 6초 시점에 `no_endpoint`로 끝난다.

대조 모드는 기존 500ms 입력 기준을 통과해 ‘질문 없이 기다리기’ 안내를
낸 뒤, 완전히 읽은 20ms 질문 프레임을 최대 75개 관찰한다. 이는
1,500ms 분량의 PCM이다. 프레임 한도까지 발화 종료가 없고 해제까지
정상이면 `no_endpoint`로 기록한다. 마지막 프레임에서 발화 종료가
검출되면 `endpoint`를 우선한다. 전체 한도, 질문 경로의 기존 상한,
STOP으로 완료되지 않은 관찰은 `stopped`다. 읽기 오류와 코덱 해제 실패는
각각 `read_failed`와 `release_failed`로 남긴다. 안내 이전에 질문
로컬 한도가 끝나는 경우의 `quiet_timeout`도 유지한다.

회귀에는 같은 입력의 짧은 관찰 완료와 일반 질문 제한 만료, 늦게 시작한
관찰의 전체 시간 만료, 마지막 읽기의 STOP·부분 읽기, 마지막 프레임의
`endpoint`, 기존 로컬 한도 도달 및 해제 실패를 포함했다. 기존 WakeNet
입력 상한, 일반 질문 400프레임·8초, 발화 기준과 PCM 지움은 유지한다.

대조 앱은 `K151_WAKE_ONLY_CONTROL=ON`으로 빌드하며 프로젝트 이름은
`k151_wake_only_control`이다. 수집기는 `--wake-only-control`로
실행하고 대조 전용 시작 표식·안내와 이미지별 승인을 확인한다.
CI는 별도 검토 아티팩트와 75프레임·10초 한도가 적힌 manifest를 생성한다.
이 변경의 검증 범위는 오프라인 시험과 컴파일이다. 실제 설치에는
새 이미지의 사전 검토와 승인이 필요하다.

## 호출어 수신 시간 오류 진단

이전 실물 V2에는 `capture_clock`만 있어 5.173초의 호스트 기록으로
어느 시간 조건이 작동했는지 특정할 수 없다. 보고서 V3은
`fault`와 `capture_clock`에 고정 값 `clock_reason`을 추가한다.

| 값 | 해당 경계 |
|---|---|
| `invalid_start` | 수신 시작 시각이 음수 |
| `clock_rollback` | 다음 단조 시계값이 이전 값보다 작음 |
| `poll_gap_exceeded` | 최초 폴링까지 또는 폴링 시작 사이의 간격이 100ms 초과 |
| `poll_duration_exceeded` | 한 폴링이 시작한 뒤 100ms 초과 |
| `capture_window_exceeded` | 폴링 도중 시작으로부터 5초 초과 |

동일 검사에서 여러 조건이 겹치면 이전 검사 순서대로 시계 후퇴,
100ms 처리 초과, 5초 초과를 평가한다. 폴링 내부에서 확인한 첫 위반을
보존하므로 시계값이 정상으로 돌아와도 일반 `wake_input` 오류로
기록하지 않는다. 새 폴링 전에 5초에 도달하면 기존처럼 미감지로 종료한다.
100ms와 5초 비교, 500프레임 상한, 전체 START 10초, 대조 1.5초는
변경하지 않았다.

모의 I2S와 WakeNet으로 각 사유를 재현했다. 한 번 후퇴한 뒤 정상값으로
돌아오는 경우에도 `clock_rollback`을 유지했다. 정확히 100ms와
정확히 5초에서는 기존 결과를 내고, 한도를 넘으면 해당 사유를
기록하는 것을 확인했다. 호스트는 기존 V1·V2 레코드도 읽으며, V3의
시간 오류에서만 허용 목록의 `clock_reason`을 받는다. 시간 오류가
나면 질문 구간은 `not_run`이다. 이 작업에서는 실물에 쓰거나
실물 시험을 다시 하지 않았다.

확인하고 `endpoint`와 종료 HOLD를 받으면 이번 실물 시험의 성공으로
기록한다. `no_endpoint`, `stopped` 및 오류는 검출 성공과 별도로 기록한다.
실제 음성은 RAM에서 처리하고 지운다. 음성 파일 저장, 외부 전송,
스피커 재생, 유료 API 호출은 시험 범위에서 제외한다.

| 검토 항목 | 값 |
|---|---|
| 질문 이미지 SHA256 | `a418a3e83313309b4158159a1415e8aa238fd10f3c6ec8243419a86f74c9114b` |
| 임시 쓰기 | `ota_1 [0x510000,0x5BD630)`, 710,192바이트 |
| 섹터 지우기 | `ota_1 [0x510000,0x5BE000)`, 712,704바이트 |
| 복구 | `ota_1 [0x510000,0xA00000)`, 5,177,344바이트 |

원본 전체 백업 두 파일의 크기와 SHA256, 각 파일의 `ota_1`과 복구

보였다. 승인 뒤 쓰기 전 같은 기기, 보안 설정, 표·OTA 선택 데이터와
출고 슬롯을 실제로 대조한다. 쓰기 범위는 `ota_1`에 한정한다.
설치 쓰기가 시작되면 시험 결과와 관계없이 검토한 복구 절차가 실행된다.
복구 슬롯의 독립 검증과 표·OTA 선택 데이터 일치가 확인된 경우에만
출고 부팅을 요청한다. 복구 조건이 불일치하거나 독립 검증에 실패하면
추가 쓰기와 출고 부팅을 중단한다.

Windows 오프라인 회귀는 C++ 테스트를 포함해 1,393건 통과, 7건 건너뜀이다.
실행기 모의 시험 11개에서 검출 성공, 미검출, 중단, 시간 오류,
설치 일부 실패, 시험 부팅·수집 오류 뒤의 복구를 확인했다.
복구 실패 시 출고 부팅 차단과 실행기 재사용 거부도 확인했다.
이 준비 단계는 실물에 이미지를 쓰거나 포트를 열어 리셋하지 않았다.

호출어 폴링 도중 5초 수신 한도를 넘었다. 질문 안내와 질문 수신이
시작되지 않아 이번 시험에서 발화 종료를 평가하지 못했다. 실제 음성
파일 저장, 외부 전송과 유료 API 호출은 없었다. 같은 승인으로 다시
실행하지 않았다.

결과를 기록한 뒤 원본 `ota_1 [0x510000,0xA00000)` 전체
5,177,344바이트를 복구했다. 복구 digest는 검토한 원본 슬롯과
일치했고, 파티션 표와 OTA 선택 데이터는 설치 전·시험 뒤·복구 뒤
일치했다. 출고 재부팅을 요청하고 정상 COM3 USB Serial/JTAG의 복귀를
확인했다. 사용자가 출고 얼굴 화면 복귀를 확인했다.

| 실행 | 벽시계 시간 |
|---|---:|
| 쓰기 전 원본 슬롯 검증 | 9.671초 |
| 임시 이미지 쓰기 | 12.123초 |
| 임시 이미지 독립 검증 | 1.951초 |
| 원본 슬롯 전체 복구 | 83.639초 |
| 원본 슬롯 독립 검증 | 9.688초 |

Windows 오프라인 집중 회귀 62건이 통과했다.

## V3 호출어 수신 5초 경계의 오프라인 재현

실물 V3는 `capture_window_exceeded`를 기록했다. 이 분기는 한 번의
폴링을 5초 한도 전에 시작했으나 읽기, 리샘플링 또는 WakeNet 결과
확인 중 누적 시간이 5초를 넘었을 때 실행된다. 시계 후퇴와 단일 폴링
또는 폴링 간격 100ms 초과는 별도 사유다. 수신 시작 시각은 마이크를
열고 수신 안내를 보내기 전에 잡는다. 따라서 열린 뒤 안내를 처리하는
시간과 각 폴링 시간도 5초 안에 포함된다.

실제 수신 전용 코드에 합성 PCM, 모의 코덱, 모의 WakeNet, 가상 시계를
연결했다. 시간은 수신 시작 기준이며 모델 호출 수는 모의 512샘플
청크의 집계다.

| 재현 조건 | 가상 시각과 입력 | 결과 |
|---|---|---|
| 매 읽기가 10.3ms, 모델은 계속 미감지 | 5.005800초, 읽기 486번, 모델 호출 151번 | `capture_window_exceeded`, 질문 `not_run` |
| 안내 처리 1µs, 읽기마다 10ms, 모델은 계속 미감지 | 5.000001초, 읽기 500번, 모델 호출 155번 | 마지막 PCM 읽기 뒤 모델 호출 전 제한에 도달, 질문 `not_run` |
| 마지막 청크의 모델 감지 결과가 정확히 5초에 반환 | 5.000000초, 읽기 500번, 모델 호출 156번 | 호출어 승인, 합성 질문 `endpoint` |
| 위 감지 결과만 1µs 늦게 반환 | 5.000001초, 읽기 500번, 모델 호출 156번 | 감지 결과 폐기, `capture_window_exceeded`, 질문 `not_run` |

타임아웃에서는 질문 버퍼 할당과 질문 안내 없이 코덱과 모델이 해제되는
것을 검사했다. 호스트 수집기는 표준 질문과 호출어 단독 대조에서 모두
V3 오류와 질문 `not_run`, 종료 HOLD를 처리하며 START를 한 번만 보냈다.
임시 소스 복사본에서 한도를 1µs 늘리거나, 5초와 정확히 같은 결과를
거부하는 비교식을 사용했을 때 새 회귀 시험이 각각 실패했다.

V3 오류 기록에는 입력 프레임 수, 모델 호출 수, 안내가 표시된 시각,
마지막 감지 결과가 없다. 이번 재현으로 실물 오류와 같은 종료 경로를
확인했다. 실제 발화가 모델에 어떻게 도달했는지, 미감지가 이어졌는지
또는 마지막 감지가 늦었는지는 남은 기록으로 구분할 수 없다. 원인
구분에는 이후 승인된 실물 진단에서 PCM을 저장하지 않고 읽은 프레임
수, 모델 호출 수, 한도 직전 단계를 집계하는 증거가 필요하다.

Windows 집중 회귀 284건과 전체 오프라인 회귀 1,398건이 통과했다. 전체 회귀에서 7건을 건너뛰었다.
펌웨어 동작과 5초·100ms·500프레임 제한은 유지했다. 이번 검증은
장치에 연결하거나 새 음성을 저장하지 않는 오프라인 작업이다.

## V4 호출어 수신 한도 진단

`MIC_WAKE_TRIAL_V4`는 `capture_window_exceeded` 결과에
`deadline_progress` 집계를 추가한다. 읽기가 끝난 10ms PCM 프레임 수,
반환된 WakeNet 호출 수, 마지막 모델 결과와 제한 검사 직전의 폴링
단계를 기록한다. 제한을 넘긴 읽기는 프레임 수에 들어갈 수 있고,
제한을 넘긴 감지 응답은 집계에만 들어간다. 이것을 호출어 감지로
처리하거나 질문 수신에 넘기지 않는다.

| 필드 | 의미 |
|---|---|
| `frames_read` | 성공한 10ms 읽기 수, 0–500 |
| `model_calls` | 완료된 감지 호출 수, 읽기 수 이하 |
| `last_model_result` | `not_called`, `none`, `detected`, `error` |
| `last_poll_step` | `poll_entry`, `mic_read`, `input_processing`, `model_return` 중 마지막으로 도달한 단계 |

`last_poll_step`은 마지막으로 도달한 단계를 나타내며 단계별 소요
시간을 측정하지 않는다. 예를 들어 `model_return`과 `detected`는
모델이 감지를 반환했으나 시간 검사에서 결과를 폐기했다는 뜻이다.
`mic_read`와 `none`은 마지막 입력을 읽는 구간에서 마감에 도달했고,
그 전에 완료된 마지막 모델 호출은 미감지로 끝났다는 뜻이다. 음성
샘플, 텍스트, 개별 타임스탬프는 출력하지 않는다. 호스트 수집기는
시험 종료까지 검증하고 V1–V3 기록도 계속 읽는다.

| 오프라인 재현 | V4 집계 |
|---|---|
| 10.3ms 읽기를 반복하고 모두 미감지 | `486 / 151 / none / mic_read` |
| 안내 처리 뒤 500번째 읽기에서 마감 | `500 / 155 / none / mic_read` |
| 500번째 읽기의 감지 반환이 1µs 늦음 | `500 / 156 / detected / model_return` |

정확히 5초에 반환된 감지가 합성 질문의 발화 종료까지 이어지는
회귀와, 1µs 늦은 결과에서 질문이 `not_run`인 회귀를 각각 확인했다.
형식이 틀리거나 PCM 필드를 포함한 기록은 호스트에서 거부한다.
Windows 집중 회귀 298건이 통과했다. 5초, 100ms, 500프레임, 전체
10초 한도와 운영·클라우드 기본 차단을 유지한다. 이 변경을 실물에
적용하거나 실제 음성에 사용한 기록은 없다.

## V4 실물 시험의 호출어 감지와 질문 단계 중단

검토한 V4 표준 질문 이미지로 별도 승인 뒤 실물 시험을 1회
실행했다. 이미지 SHA256은 아래와 같다.
[ESP32-S3 V4 표준 질문 이미지 빌드](https://github.com/rownlvh8875-coder/stackchan-autonomy/actions/runs/45017131766)

`1d055b4665efee53aadbee4db5117654b3b21f5987cf14da255ba7cfc74e2562`

사전 검사에서 동일 보드, 16MB 플래시, 보안 설정, 파티션 표·OTA
선택 데이터와 원본 `ota_1`이 백업과 일치했다. 임시 이미지는
`ota_1 [0x510000,0x5BD940)`에 710,976바이트를 썼다.
섹터 지우기 범위는 `[0x510000,0x5BE000)` 712,704바이트였고,
진단 부팅 전에 임시 이미지를 독립 검증했다.

| 실물 항목 | 결과 |
|---|---|
| 호출어 수신 안내 | 수신 |
| 호출어 `MIC_WAKE_TRIAL_V4` | `detected`, `complete` |
| 입력 집계 | 10ms 프레임 260개, 전부 0인 프레임 6개, PCM16 끝값 샘플 0개 |
| 질문 수신 안내 | 수신 |
| 질문 `MIC_QUESTION_TRIAL_V1` | `stopped` |
| 코덱 해제 불확실성 | 두 단계 모두 `false` |
| 종료 HOLD | 수신 |
| START 의도 기록부터 결과 저장까지 | 10.028초 |

호출어 단계에서 `capture_window_exceeded`가 발생하지 않아 V4의
`deadline_progress`가 붙지 않았다. 질문 단계 중단 시점은 START의
10초 전체 제한과 일치한다. 질문 프로토콜 V1은 `stopped`의 세부
사유나 발화 시작·종료 상태를 별도로 기록하지 않아 실제 질문의
발화 종료는 미확인이다. 외부 전송, 유료 API 호출, 음성 파일 저장과
스피커 재생은 없었다.

원본 `ota_1 [0x510000,0xA00000)` 전체 5,177,344바이트를
복구하고 백업과 독립 digest가 일치함을 검증했다. 파티션 표와 OTA
선택 데이터는 설치 전·시험 뒤·복구 뒤 일치했다. 출고 재부팅을
요청하고 정상 COM3 USB Serial/JTAG 복귀를 확인했다.
