# 직접 연결 개발을 위한 확인 자료 — 2026-11-18

날짜는 Asia/Seoul 기준. 사용자가 제조사 문의를 취소하고 **지원 경로가 없으면
직접 만들라**고 지시했다. 외부 문의는 게시하지 않았고 로컬 게시 대기 파일도 제거했다.
이 문서는 개발 전 근거 정리이며 새 펌웨어가 설치되거나 실물 관찰 연결이 성공한 기록은 아니다.

## 재사용할 기존 구현

- `firmware/observer/`: SCOB v1 프레이밍·요청 일치·사진/센서 읽기 모듈과 실제 ESP32-S3 빌드.
- `src/stackchan_autonomy/observer_protocol.py`, `observer.py`, `observer_async.py`:
  기기 페어링, 길이·CRC·JPEG·해시·출처·최신성 검증 및 비동기 연결.
- GPT 이미지 도구와 모델/전송 opt-in·요청 예산·취소 처리는 이미 구현돼 있다.
  실제 사진 입력·실물 설치는 아직 검증하지 않았다.

새 통신 규약을 중복 작성하기보다 이 경로를 재사용하는 것이 우선 후보다. 다만
기기에서 실제로 이 규약을 처리하는 펌웨어가 실행되어야 한다. 출고 상태의 USB ROM
읽기와 공식 앱 카메라 표시는 이 런타임 규약을 제공하지 않는다.

## 직접 개발과 공식 앱 호환성의 구분

관찰/제어 인터페이스는 직접 구현할 수 있지만, 제조사 비공개 인증 구현이 자동으로
생기는 것은 아니다. 독립 개발 모드의 공식 앱 기능은 보장하지 않는다. 현재 원본 기기는
바꾸지 않았으며 원본 A/B·정상 부팅·기존 앱/GPT·공식 카메라 확인은 그대로 유지한다.
이후 사용자는 **공식 앱은 필수가 아니며 원하는 기능이 제대로 동작하면 된다**고
확인했다. 최종 목표는 공식 앱에 종속되지 않는 전용 기능과 로봇 자체 GPT API 연결이다.

## 소스에서 먼저 확인한 보존 조건

고정 소스: `m5stack/StackChan`의
`28b9f0c8bd6acd81cb3c70f1a93c3e373b39d400`.

- `firmware/partitions.csv`에는 NVS·OTA 데이터·두 OTA 앱 슬롯·assets·coredump가 있다.
  최초 소스 검토 뒤 사용자가 아래 도구로 실제 백업의 일치 배치를 확인했다.
  배치만으로 실제 여유 슬롯이나 원본 앱을 보존하는 설치 주소를 확정하지 않는다.
- `firmware/main/hal/hal.cpp`의 HAL 초기화는 NVS 초기화 오류 일부에서
  `nvs_flash_erase()`를 호출한다. 독립 개발용 이미지에는 설정 자동 삭제를 막는
  실패 처리가 필요하다. 같은 초기화는 서보 초기화도 호출하므로 관찰 코드의
  읽기 전용 계약만으로 기기 전체 무동작을 주장하지 않는다.
- `firmware/xiaozhi-esp32/main/main.cc`에도 NVS 초기화 오류의 자동 삭제 경로가 있다.
  현재 StackChan 엔트리포인트의 호출 여부와 별개로 독립 엔트리포인트를 만들 때 감사한다.
- 기존 USB 관찰 작업자는 HAL 초기화 뒤에 시작된다. 제조사 서비스를 실행하지 않는
  개발 모드라면 초기화·UI/음성·실패 처리까지 일관되게 정해야 한다.

## 현재 경계

제품 런타임·기기·NVS·부트 선택·파티션을 변경하지 않았다. 원본 백업은
사용자 노트북에만 있으며 에이전트가 원본 바이너리나 키·NVS 값을 받거나 해석하지 않았다.
실제 복구 쓰기와 별도 저장장치 사본은 미확인이다. 새 이미지 설치는 정확한 바이너리·
실제 파티션 배치·기존 기능 영향·복귀 절차를 검토한 뒤 별도로 결정한다.

## 독립 GPT 모드에 앞서 확인한 하드웨어 결합

기존 관찰 빌드에 준비한 위 고정 StackChan 소스와 적용된 Xiaozhi 패치에서 확인했다.
아래는 소스 검토 결과이며, 독립 모드의 설계 승인·구현·실물 동작 결과가 아니다.

| 재사용 후보 | 그대로 가져올 때 남는 문제 |
|---|---|
| `firmware/main/hal/board/stackchan.cc`의 전원·I2C·AW9523·LCD·카메라 초기화 | 보드 생성자에 터치 타이머·전원 절약·설정 복구도 결합돼 있다. 필요한 초기화를 분리해야 한다. |
| 같은 파일의 `StartWifiConfigMode()` | `GetHAL().requestAppSetup()`으로 공식 앱 설정 화면을 요청한다. 앱을 쓰지 않는 모드는 독립적인 Wi-Fi/API 키 설정 경로가 필요하다. |
| `firmware/main/hal/board/config.h`와 `cores3_audio_codec.cc` | 입력·출력 기본24kHz, 마이크/참조 채널과 TX의32bit 슬롯을 고려해야 한다. PCM16 모노를 I2S 원시 버퍼와 같다고 가정하지 않는다. |
| `CoreS3AudioCodec::Read()` | 읽기 오류를 로그만 남기고 요청 샘플 수를 반환하는 경로가 있다. 새 녹음 경로는 유효 샘플/오류를 구분해야 하며, 성공으로 처리해 전송하지 않는다. |
| `xiaozhi-esp32/main/audio/audio_codec.cc` | 기본 볼륨을 기존 `audio` NVS에서 읽고 변경 시 쓴다. 원본 설정을 보존하는 새 설정 저장 계약이 필요하다. |
| `firmware/main/hal/hal.cpp`의 OTA 확인 | 실행20초 뒤 이미지를 유효 처리하는 기존 경로가 있다. 경과 시간만으로 독립 GPT 모드의 부팅·기능 검증을 대신하지 않는다. |

따라서 단순히 기존 앱의 모델 이름을 GPT로 바꾸는 작업으로 해결되지 않는다.
로봇의 ESP-IDF/C++ 실행 경로에 독립적인 설정·Wi-Fi/TLS·음성 입출력·OpenAI 요청을
구현해야 한다. Python SDK·SQLite 엔진을 ESP32에 그대로 설치하는 방식은 아니다.
기존 PC 구현의 요청 예산·중지·메모리 제한과 관찰 규약은 재사용할 계약의 근거가 된다.

제안하는 검증 순서는 실제 배치 확인 → 독립 부팅/설정과 직접 GPT 통신 →
마이크 전사/GPT/스피커 대화 → 카메라·센서 관찰 → 자율 판단/물리 동작이다.
이 순서는 개발 제안이다. 첫 직접 통신 성공을 음성·자율 동작 완성으로 취급하지 않는다.
음성 전사·GPT 응답·음성 합성은 별도 API 요청이므로, 기존 텍스트 한도와 같은
비용이라고 가정하지 않고 새 요청 예산을 설계해야 한다.

현재 실제 단말의 빈 슬롯·활성 슬롯·사용 가능 RAM과 독립 TLS/음성 동시 동작은
미확인이다. 원본 슬롯을 남길 수 있다는 약속이나 설치 주소를 이 검토에서 만들지 않는다.

## 읽기 전용 진단 시제품

직접 만들어 보자는 요청의 첫 실험으로
[`inspect_layout.py`](../../experiments/k151_layout_spike/inspect_layout.py)를 추가했다.
검증된 원본 A의 SHA256과 대조하고 파티션 표의 MD5·범위·겹침을 검증하며, 파티션
주소·크기·형식만 출력한다. 슬롯 개수로 활성/빈 슬롯이나 설치 안전성을 추측하지 않는다.
`.env`·USB·네트워크·쓰기 기능은 없고 비표준 파티션 이름은 가린다.
제품 CLI나 배포 패키지에 통합하지 않은 실험용 도구다.

합성16MB 파일만으로 표준 표 파싱, 잘못된 SHA, 일치 SHA를 가진 MD5 변조,
겹치는 범위, 잘린 파일, 비표준 이름 가림, 실제 CLI/고정 오류/입력 불변을 확인했다.
Ruff 검사·format·공백 검사는 통과했다. 이후 사용자가 도구를 실행해 원본 SHA·표 MD5
일치와 실제7개 파티션·각5,177,344B 앱 슬롯2개를 보고했다.
[실제 출력 기록](2026-11-18-k151-backup-layout.json)은 원본 바이너리 없는 사용자 증거다.
활성/빈 슬롯과 설치 안전성은 여전히 미확인이다. 이 시제품의 검증을 기기 관찰·실물 설치
성공으로 판정하지 않는다.
