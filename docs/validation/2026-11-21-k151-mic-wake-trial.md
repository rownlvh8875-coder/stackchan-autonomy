# K151 마이크 단독 WakeNet 1회 진단

## 종료 결과 V2

새 종료 결과 `MIC_WAKE_TRIAL_V2`는 기존 결과에 `stage`와
`codec_cleanup_unverified`를 붙인다. 종료 상태와 함께 아래 고정값만
사용한다.

| 과정 | `stage` |
|---|---|
| 동의·입장 및 메모리 확인 | `admission`, `baseline_memory`, `resident_memory` |
| 모델 준비, 포맷 확인, 리셋 | `model_prepare`, `input_format`, `model_reset` |
| I2C 버스, 보드 전원, 앰프 리셋, 보드 핸들 반납 | `i2c_bus`, `board_power`, `amplifier_reset`, `board_release` |
| I2S 수신, 코덱 준비, 열기·입력 게인 | `i2s_rx`, `codec_prepare`, `codec_open` |
| 시간 검사, PCM 읽기, WakeNet 입력 처리 | `capture_clock`, `capture_read`, `wake_input` |
| 코덱 해제 후 완료 | `codec_release`, `complete` |

앞 단계에서 오류가 난 뒤 해제도 확인하지 못하면 앞 단계의 코드와
`codec_cleanup_unverified:true`가 함께 남는다. 앞 단계가 정상 완료된
뒤 해제가 실패한 경우 `codec_release`를 사용한다. 드라이버의 원시 오류
문자열이나 PCM은 결과에 포함하지 않는다. 프레임 집계는 정상 종료 때만
남는다. 호스트는 보관된 V1 레코드도 원래 형식으로 읽는다. 이전 실물
시험에서 받은 V1 `fault`의 정확한 실패 단계는 여전히 미확정이다.

`K151MicWakeTrial`은 실물 마이크 검증용 코드다. 모델을 준비한 로컬 소유
작업에서 한 번 호출할 수 있다. ESP32-S3 HOLD 앱의 구성 요소로 컴파일되며
부팅 시에는 실행되지 않는다. 이번 변경의 검증은 Windows 호스트의 모의
I2C/I2S와 모델에서 실행했다.

## 진단 경계

- 현재 보드 식별과 독점 I2S0 소유가 확인되어야 한다. 최신 시도에서는
  수신 채널 할당 전에 펌웨어가 전원 설정과 앰프 리셋을 확인한다. STOP과
  로컬 동의 철회는 해제가 끝날 때까지 유지한다.
- 호출자는 검증된 로컬 `K151WakeNetPort`를 독점 준비하고 소유권을 넘긴다.
  진단은 16kHz mono PCM16과 160–2048 샘플 chunk를 검사하고 새 모델
  컨텍스트를 만든 뒤 ES7210 수신을 시작한다. 모델은 진단에서 해제한다.
- 기존 `K151MicReader`와 `NativeWakeInput`에서 24kHz mono PCM16의
  10ms 프레임을 공통 FIR로 변환한다. 최대 5초·500프레임, poll 시작
  간격과 실행 시간 100ms 상한을 검사한다. 타이머 역행이나 늦은 poll은
  오류다. 동기 드라이버·모델 호출을 강제로 선점하는 방식은 아니다.
- 반환값은 거부, 중단, 미감지, 감지, 오류 중 하나다. 입력 버퍼는 기존
  volatile 지움 경로를 사용한다. 감지는 코덱 종료와 모델 해제, 최종
  STOP·동의 검사까지 성공해야 반환된다. 스피커, cloud, 대화 세션
  권한, 음성 파일을 다루는 경로는 진단에 연결되어 있지 않다.

## 오프라인 검증

진단 진입점을 호출하는 시험을 먼저 실행해 새 구현이 없는 상태의 실패를
확인했다. 코덱 C ABI 모의에서 정상 감지, 증거·동의 부족, 잘못된 모델
포맷, 모델 reset·detect 실패, short read, 시계 오류, 늦은 detect,
코덱 닫기와 인터페이스 삭제 반환 오류를 주입했다. 독립 검토에서 발견한
삭제 반환 누락을 재현한 뒤, 다른 해제를 계속하고 실패를 보존하게 수정했다.
시작·reset·open·read·detect·close·모델
해제의 STOP과 detect 중 동의 철회, 같은 객체에서 두 번째 실행 거부도
검사했다. 모의 모델은 512샘플 수신, RX 전용 실행, 모델 해제 전에 코덱
리소스가 정리되는 순서를 검사했다. 5초 제한은 250프레임에서, 프레임
제한은 0.5초에 500프레임을 처리하는 별도 입력에서 검사했다.

## 순정 인식을 기준으로 한 첫 실물 시험

현재 출고 펌웨어에서 음성이 잘 인식된다고 사용자가 확인했다. 이 관찰과
제조사 보드 설정을 첫 수신 전용 시험의 기준으로 삼는다. 전원·클록·스피커
출력 파형 측정은 이상 원인을 좁힐 때 쓰는 방법으로 남긴다.
[제조사 K151 보드 설정](https://github.com/m5stack/StackChan/blob/28b9f0c8bd6acd81cb3c70f1a93c3e373b39d400/firmware/main/hal/board/config.h)

수신 전용 코덱은 같은 I2C 버스에서 AXP2101 식별자와 ALDO1/2 활성 설정을
읽는다. AW9523 식별자, P0_2 GPIO 모드와 출력 방향을 확인한 뒤 그 비트만
내리고 출력 래치를 다시 읽는다. 앰프 리셋은 시험 종료까지 유지한다.
설정 불일치, 읽기·쓰기·해제 오류나 STOP이 있으면 I2S 채널을 열지 않는다.
기존 TX와 클라우드 경로는 1회 시험에서 제외한다.
[제조사 앰프 리셋 코드](https://github.com/m5stack/StackChan/blob/28b9f0c8bd6acd81cb3c70f1a93c3e373b39d400/firmware/main/hal/board/stackchan.cc#L213)
· [K151 회로도](https://m5stack-doc.oss-cn-shenzhen.aliyuncs.com/490/Sch_M5_CoreS3_v1.0.pdf#page=4)

SDK 모의에서 잘못된 칩 식별, 전원 설정, GPIO 모드·방향, 읽기·쓰기 오류,
다른 래치 값, 쓰기 중 STOP, 장치 해제 실패와 이미 리셋된 경우를 확인했다.
I2C 장치가 사용 중이라 해제되지 않으면 핸들을 보존하고 종료 경로에서
해제를 다시 시도한다. 첫 오류는 그대로 남기며 I2S에는 진입하지 않는다.
래치 검사는 레지스터 상태에 대한 증거이며 실제 인식은 1회 시험에서
“Hi StackChan” 감지와 집계로 확인한다. 별도 이미지의 SHA256, 변경·복구
범위와 중단 조건을 정한 뒤 설치 승인을 받아 시행한다.

## 2026-11-22 검증된 내장 모델 연결

`run_embedded`는 같은 진단 수명에서 로컬 동의, STOP, 현재 보드의 전기 및
I2S0 소유 증거를 확인한 뒤 `K151WakeNetPort::prepare_embedded`를 호출한다.
기존 DROM 위치·292,607바이트·고정 SHA256과 단일 SDK 로더 검사를 통과한
모델만 같은 동의·STOP 상태로 코덱 경로에 넘긴다. 팩 검증 실패나 동의
철회 시 코덱 진입 없이 모델을 해제한다. 두 진입점은 1회 제한을 공유한다.

SDK ABI 모의에서 실제 모델 준비 코드와 연결부를 실행했다. 정상 전달,
증거·동의 부족, 사전 STOP, 팩 길이·해시 오류, 해시 중 철회, 모델 생성 중
STOP, 두 번째 시도 거부를 확인했다. 전달 이후 수신·변환·종료는 별도
코덱 ABI 모의가 기존 진단 코드로 실행했다.

ESP32-S3 HOLD 앱은 새 진입점을 링크하고 기존처럼 부팅 시 링크 확인만
출력한다. 이 이미지에는 모델 팩이 들어가지 않는다. 실제 마이크 시험에는
별도의 전기 증거, 메모리 및 이미지 검토, 기기 쓰기 승인이 필요하다.

## 2026-11-22 내부 RAM 확인

진단은 ESP-IDF heap API에서 8비트 접근이 가능한 내부 메모리의 전체 여유와
최대 연속 블록을 읽는다. 기존 기준인 각각 128KiB·32KiB를 내장 모델
로드 전과 새 컨텍스트 reset 후 ES7210 설정 전에 적용한다. 두 번째 확인은
이미 검증된 모델을 넘긴 경우에도 실행된다. 값이 부족하거나 보고된
최대 블록이 전체 여유보다 크면 `memory_denied`를 반환한다. 이때 이미
준비된 모델을 해제하고, 조회나 해제 중 STOP·동의 철회가 관측되면 중단을
반환한다. 두 번째 시도는 계속 거부한다.

SDK와 코덱 모의에서 기준값과 정확히 일치할 때의 진행, 전체 여유 1바이트
부족, 연속 블록 1바이트 부족, 일관성 없는 값, 조회 중 STOP·동의 철회를
검사했다. 모델 준비 경로의 거부는 해시 계산과 SDK 모델 생성 전에
확인했다. 모델 상주 상태의 거부는 코덱 버스 할당 전에 확인했다.

이 검사는 순간 여유를 읽는다. 실제 할당 가능 여부와 질문·TLS·TTS가
동시에 살아 있는 운영 경로의 메모리 최고 사용량은 별도 근거가 필요하다.
HOLD와 기존 마이크 전기 조건은 유지된다.

## 2026-11-22 수신 집계

기존 마이크 전용 코덱과 WakeNet 진단 사이에서 선택된 24kHz PCM16의
10ms 프레임 수, 모든 샘플이 0인 프레임 수, PCM16 최솟값·최댓값에
해당하는 샘플 수를 누적한다. 전체 진단에 대한 세 숫자만 반환하고
PCM 저장·출력은 추가하지 않았다. 값에는 물리 채널 검증, 마이크 감도,
음성 검출에 필요한 별도 해석이 필요하다.

집계는 모든 코덱 자원 해제와 모델 종료, 최종 STOP·동의 검사를 거친
정상 감지/미감지에서만 한 번 읽을 수 있다. 오류·중단·두 번째 실행
거부 뒤에는 집계가 없고 입력의 기존 버퍼 지움을 사용한다. 공통 FIR,
512샘플 모델 전달, 100ms와 5초·500프레임 상한은 보존한다.

모의 TDM에서 레퍼런스 슬롯에만 PCM16 끝값을 넣은 프레임과 선택된
마이크 슬롯에 직접 끝값을 넣은 프레임을 주입했다. 집계에는 선택한
슬롯만 반영됐고, 마지막 STOP·동의 철회·해제 실패에서도 집계가 나오지
않았다. 이번 후속에서는 실물 포트를 열거나 진단을 시작하지 않았다.

## 2026-11-22 진단 결과 형식

`format_k151_mic_wake_report`는 마이크 진단의 상태와 한 번 읽은 집계를
`MIC_WAKE_TRIAL_V1` JSON 한 줄로 만든다. 정상 감지·미감지에는 프레임
집계 세 항목이 들어가며, 중단·오류·거부·메모리 부족에는 상태만 들어간다.
`operating_admission`은 항상 false다. 출력 버퍼에 한 줄이 들어가지 않으면
첫 바이트를 비워 부분 줄의 사용을 막는다.

호스트의 `parse_mic_wake_trial_report`는 이미 디코딩된 레코드에서 여섯
상태, 필드 집합, 1–500프레임, 0인 프레임 수와 PCM16 끝값 샘플 수의
상한을 확인한다. 원본 PCM이나 추가 필드를 받는 경로는 없다.
선택된 코덱 입력의 모의 정상 감지와 모델 해제 중 STOP 결과를 실제 C++
형식화 함수로 출력해 같은 호스트 파서에 통과시켰다. 손상된 값과 잘린
출력도 거부했다.

이번 변경은 HOLD의 기동 동작을 유지한다. 실물 마이크 시험용 실행 연결과
계측은 해당 보드의 전기·소유권 증거를 갖춘 별도 단계에서 진행한다.

## 2026-11-22 통합 모의 시험

하나의 실행 파일에서 실제 `run_embedded`와 `run_prepared`를 사용한다.
기존 모델 SDK·ES7210·I2S 모의 경계에 입력을 공급하고, 생산 코드의 팩
검증 비교·모델 재생성·24kHz 수신·공통 FIR·512샘플 WakeNet 전달·정리·
JSON 형식화를 연결한다. 같은 레코드를 Python 호스트 검사기로 읽는다.
PSA 다이제스트와 WakeNet의 검출 결과는 해당 SDK 모의가 공급한다.

정상 모의 검출은 10ms 프레임 네 개를 소비한다. 틀린 다이제스트와 새 모델
상주 후 내부 메모리 부족은 코덱을 열기 전에 멈춘다. 첫 부분 읽기는 추론에
도달하지 않으며, SDK가 감지를 반환하는 중 STOP이면 수신 집계를 반환하지
않는다. 각 시험에서 SDK 모델·I2S·버스 해제와 재시도 차단을 확인했다.
생산 코드와 실물 기동 상태는 바꾸지 않았다.

## 2026-11-22 호출어 뒤 질문 진단

`K151_QUESTION_TRIAL=ON`으로 만든 별도 `k151_mic_question_trial`은
기존 호출어 감지와 코덱·모델 해제가 완료된 경우에만 질문 단계로
넘어간다. 384,000바이트를 PSRAM에서 확보한 뒤 AMP 리셋과 보드
레지스터를 다시 확인하고 새 I2S RX 채널을 연다. 이전 채널의 호출어
프레임은 질문 처리에 쓰이지 않는다. 기본 호출어 이미지의 시작 표식과
질문 이미지의 시작 표식은 다르며 기존 호출어 수집기는 질문 이미지의
START를 보내지 않는다.

`QUESTION_NOW` 뒤 기존 `MicFrameBridge`로 24kHz 10ms 프레임 두 개를
결합한다. `QuestionCapture`는 기존 RMS 설정과 60ms 음성 시작,
500ms 무음 종료 기준을 사용한다. 질문은 최대 400개의 20ms 프레임과
8초의 단조 시계로 제한된다. START부터 걸리는 기존 10초 시험 제한도
유지되므로 호출어 감지까지 걸린 시간에 따라 질문에 남는 시간이 짧아질
수 있다. 실제 환경에서 이 발화 종료 기준의 정확도는 아직 측정하지
않았다.

정상, 시간 만료, STOP, 동의 철회, 오류에서 RAM의 PCM을 지운다.
질문 결과는 `MIC_QUESTION_TRIAL_V1`의 고정 상태와 코덱 해제 불확실성만
반환한다. 호출어와 질문의 결과를 각각 출력한 뒤 HOLD로 전환한다.
호스트 시험은 실제 포트 코드에 합성 PCM과 코덱·I2S 응답 모의를
공급했다. 정상 종료, 미감지, PSRAM 거부, 시간·프레임 상한, STOP,
동의 철회, 부분 읽기, 시계 후퇴, 해제 실패 및 PCM 지움을 검사했다.

CI는 별도 프로젝트 이름과 SHA256·DROM 모델 팩·`ota_1` 경계를 검사한
리뷰용 아티팩트를 제공한다. 기존 USB 수집기의 `--question` 모드는
질문 전용 승인과 독립 설치 검증을 요구한다. 새 시작 표식에만 START를
한 번 보내고 두 결과와 종료 HOLD를 검증한 뒤 고정 필드만 저장한다.
실물 시험에는 이미지별 설치·복구 검토가 필요하다. 이 진단의 USB
출력에는 PCM이 없고, TX·네트워크를 열지 않는다. 실물 질문 녹음과
스피커 재생, 독립 GPT 대화는 검증 전이다.
